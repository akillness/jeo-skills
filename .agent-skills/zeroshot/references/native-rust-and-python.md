# Standalone Rust CLI and Python SDK

## Keep the native product separate

`zeroshot-rust` is an independent product in the same repository. It is not a faster
implementation of every Node command. Its graph, target, runtime, output, state, and
release contracts are native-owned.

Choose this lane when the user needs one or more of:

- Windows support;
- JSON for single-result commands and NDJSON for streams;
- exact graph and runtime JSON;
- a local native controller;
- a named or direct target;
- stable submission idempotency;
- the typed async Python client;
- a self-hosted target image.

Choose the Node product for its established guided setup, broad issue-source detection,
Node provider registry, worktree/Docker UX, `resume`, trace/semantic export, and PR
workflow unless the native contract is specifically required.

## Installation and live contract

At the audit:

```bash
npm install -g @the-open-engine/zeroshot-rust@0.4.0
zeroshot-rust version
zeroshot-rust --help
```

The npm package downloads a platform archive and verifies it with release
`SHA256SUMS`. Supported hosts were Linux x64/arm64, macOS x64/arm64, and Windows x64.
Unsupported hosts fail closed.

The generated CLI document is the source-backed reference:

- `docs/zeroshot-rust-cli.md`
- generated from the typed Clap command model;
- regenerated by the repository example, not edited by hand.

Recheck `zeroshot-rust --help` because native releases are versioned independently of
the Node package.

## Main native commands

Read-only or validation-first surfaces:

```bash
zeroshot-rust template list
zeroshot-rust template show software-change
zeroshot-rust list
zeroshot-rust status <run-id>
zeroshot-rust watch <run-id>
zeroshot-rust logs <run-id>
```

Mutation or execution surfaces:

```bash
zeroshot-rust run ...
zeroshot-rust force-stop <run-id>
zeroshot-rust target add ...
zeroshot-rust target login ...
zeroshot-rust target setup ...
zeroshot-rust target serve ...
```

Single-result commands write JSON. Foreground `run`, `watch`, `logs`, and `attach` stream
NDJSON. Ctrl+C detaches from foreground observation without stopping the run. Use
`force-stop` only after identifying the run and confirming interruption.

## Build a source-neutral run contract

A native submission needs:

- human-readable title;
- input JSON file;
- built-in template or exact graph JSON;
- exact runtime config or one uniform runtime config;
- optional target and branch;
- optional stable submission key;
- explicit delivery mode;
- explicit detach choice.

Example validation only:

```bash
zeroshot-rust run \
  --title 'Add JSON output with tests' \
  --input input.json \
  --template software-change \
  --uniform-runtime-config runtime.json \
  --validate-only
```

`--validate-only` materializes and validates without submitting or contacting a target.
Run it before user approval. Show the resulting topology, provider/model plan,
environment names, and delivery consequences.

Do not put a prompt string where `--input` expects a JSON file. Do not put secrets in
input, graph, or runtime JSON.

## Built-in templates

At the audit the native CLI advertised:

- `single-worker`: one general-purpose worker;
- `software-change`: review, validation, and optional delivery for code changes.

Inspect the live materialized template before binding runtimes:

```bash
zeroshot-rust template show software-change
```

`--pr`, `--ship`, or `--delivery` materializes native-owned delivery bindings. When a
template owns those bindings, do not also provide a same-named agent runtime binding.

## Runtime configuration

Runtime JSON is secret-free. Each executable graph node needs a same-named binding.
Agent bindings require kind and model. The audited harness/provider pairs were:

- Codex harness with OpenAI or OpenRouter;
- Claude harness with Anthropic or OpenRouter.

Sizes, model ids, and effort values are versioned. Read them from the live help rather
than copying old lists into automation.

`env` contains names copied from the submitting process. Review every name. If a node
does not need a credential, do not declare it. A uniform config can widen the same
environment across all executable nodes, so compare the expanded plan to the exact
node list.

## Local and named targets

Without `--target`, native runs use the local controller and current repository. This is
not Node worktree isolation. The Python SDK documentation is explicit that `LocalTarget`
agents mutate the selected workspace in place.

A named target adds remote source checkout, durable state, and delivery. Before using it:

1. inspect registered target origin;
2. confirm repository and default branch;
3. decide direct versus hosted authentication;
4. review `GH_TOKEN` forwarding;
5. validate graph and runtime locally;
6. use a stable `--submission-key` when a retry could duplicate submission;
7. get user approval for remote execution and delivery.

`target setup` changes only the local target registry. It does not configure the remote
server.

## Serving a target

The target server requires listen address, public origin, and storage directory:

```bash
zeroshot-rust target serve \
  --listen 127.0.0.1:8080 \
  --public-origin http://127.0.0.1:8080 \
  --storage /private/path/zeroshot-state
```

Without `--bootstrap-key-file`, it accepts unauthenticated direct connections. Bind to
loopback for a local direct target. Do not expose it on `0.0.0.0`, a LAN, tunnel, or
public host without an explicit authentication, TLS, firewall, storage, and incident
plan.

With a bootstrap key, the server consumes and removes the key file while starting.
Prepare a private regular file outside repositories and shared temporary directories.
Never pass the key value on the command line or put it in the runtime document.

## Native delivery

For the software-change template:

- `--pr` materializes pull-request delivery;
- `--ship` materializes merge delivery;
- named-target delivery can forward `GH_TOKEN`;
- the provider receives `GH_TOKEN` only when its runtime declares the name.

Treat `--ship` as an external merge approval. Read back the hosting platform after the
run. A terminal JSON result is not proof that branch protection, merge queue, or issue
closure reached the expected state.

## Observation and interruption

Use opaque cursors from `watch` and `logs` to resume streams. Do not invent numeric
offsets. The native command's NDJSON records are machine contracts, so parse complete
lines and preserve unknown fields for forward compatibility.

A timeout or cancelled observer does not imply the run stopped. Check `status`. Use
`force-stop` only after user approval or a clearly authorized incident response.

## Python SDK contract

The source SDK imports as `zeroshot` and controls the Rust sidecar. It offers:

- typed async `Client`;
- `LocalTarget` and unauthenticated `DirectTarget`;
- built-in presets or exact graph specs;
- uniform or exact runtime plans;
- durable `Run` handles;
- resumable watch and log streams;
- timeout that returns a still-active run;
- explicit `force_stop` as the lifetime-changing operation.

Python does not own or copy the graph schema, preset registry, provider/model registry,
or semantic validation. Rust stays authoritative.

At the audit, the source README's `pip install zeroshot-rust` command was not available
from PyPI: the JSON registry endpoint returned 404, and the release workflow had failed
at trusted publishing after successfully building wheels. Recheck publication before
using the command.

When source-building a wheel, follow the repository's Python CI lane:

```bash
cd sdks/python
python -m pip install -e '.[dev]'
python -m ruff check src tests examples
python -m ruff format --check src tests examples
python -m mypy src examples
python -m pytest
python -m mkdocs build --strict
```

Building or installing a source wheel is a development task, not blanket skill setup.

## Native completion packet

Report:

- native release version;
- local, direct, or named target;
- target origin and authentication class without secrets;
- repository and branch;
- graph or template digest;
- runtime config digest and environment names;
- submission key;
- delivery mode;
- terminal status and aggregate usage;
- independent validation evidence;
- whether a force-stop or observation timeout occurred;
- hosting-platform readback for PR or ship.
