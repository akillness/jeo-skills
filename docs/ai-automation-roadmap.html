01 · Overview

왜 지금 AI 자동화가 다른가

과거의 AI 자동화는 챗봇에게 질문에 답하게 하는 것이었다면, 지금의 AI 자동화는 AI가 업무를 수행하는 방향으로 진화하고 있다. 반복 업무는 AI가, 전략 수립과 감독, 최종 결정은 인간이 담당한다.

시대의 이동 한 문장. 자동화의 대상이 개별 작업(task)에서 업무 프로세스(workflow)로 이동했다.

  • 과거(챗봇 시대) — 사람이 질문하고, AI가 답했다. 예: "이 정책 어디에 나와 있어?" AI는 검색과 요약만 담당했다.
  • 지금(에이전트 시대) — 시스템이 트리거를 감지하고, 맥락을 해석하고, 도구를 호출하고, 필요하면 사람에게 승인을 요청한다. 예: 고객 환불 요청이 오면 AI가 요청을 분류하고, 정책을 근거로 제시하고, 금액이 임계값 이상이면 담당자 승인을 요청한다.

Gartner는 task-specific AI agents가 엔터프라이즈 애플리케이션의 상당 비율로 확산될 것을 전망했고, McKinsey는 2025년에도 agentic AI를 scaling하는 조직과 experimenting하는 조직이 동시에 존재한다고 보았다. 그리고 실제 운영(프로덕션) 사례 분석에 따르면, 현실에서 돌아가는 시스템 대부분은 사전에 정의된 구조화된 워크플로우에 속한다 — 자율적인 매직이 아니라, 잘 설계된 프로세스다.

따라서 이 로드맵은 기술의 깊이를 먼저 쌓고, 그 위에 실행 전략을 얹는다. 기술이 깊을수록 자동화가 신뢰받고, 실행이 명확할수록 성과가 남는다.

핵심 원칙 — 워크플로우를 먼저 고르고, 도구는 그다음이다.

Start with the workflow, not the tool Define the business outcome Check the data Build the guardrails Keep humans in control

도구(Framework, 벡터DB, 에이전트 플랫폼)를 먼저 고르면 흔히 "용기를 두고 요리를 고르는" 실수를 한다. 먼저 "어떤 프로세스의 어떤 결과를 바꿀 것인가"를 묻는 조직만 성공한다.

02 · System One

Jev — AI 자동화의 원자(原子)는 "판단"이다

이 문서는 Jev(System One) 관점에서 다섯 계층을 읽는다. 아키텍처가 아무리 복잡해도, 그 내부는 수많은 좁은 판단(narrow judgment)의 합이다. 판단의 단위가 곧 계층의 단위다.

Jev는 자유문장(text)을 생성하는 모델이 아니다. 자연어를 이해해서 타입이 붙은 선택과 확률(probability)을 돌려주는 System One 모델이다. 흐름은 언제나 같다.

// 자동화 시스템의 공통 흐름 — 어떤 계층이든 이 다섯 걸음이다
1. 코드가 일을 잘게 쪼갠다            (workflow 소유)
2. 판단에 필요한 state를 채운다       (문서 · 이력 · 정책 · 현재 상황)
3. 좁은 질문 하나를 던진다            (Choice · Noul · Score)
4. 타입 안전한 답 + confidence를 받는다
5. 코드가 임계값으로 다음 행동을 결정한다 (실행 or 사람에게 escalation)

핵심 분업은 이것이다. 모델은 판단만 하고, 코드가 기억·계산·실행·검증을 소유한다. 자동화를 "AI에게 맡긴다"는 말은, 엄밀히는 "AI의 판단 위에 사람이 검증하는 실행 구조를 세운다"는 뜻이다.

State

판단의 재료

문서, 대화 이력, 정책, 현재 상황. 판단에 필요한 사실 전부. 재료가 부실하면 판단도 부실하다.

Question + Criteria

좁은 질문

한 번에 하나의 좁은 판단만. 선택지(criteria)를 명확히 정의한다. "이 티켓은 A/B/C 중 무엇인가?"

Choice · Noul · Score

세 가지 판단 원형

Choice=정해진 옵션 중 하나 고름. Noul=조건이 성립하는가(yes/no 확률). Score=순서 있는 척도 위의 정도.

Confidence

확신의 온도계

분포의 집중도를 요약한 값. "이 판단이 얼마나 갈렸는가"를 말할 뿐, 전체 작업의 정확성 보증이 아니라는 점이 오해의 주 원인이다.

Escalation

사람에게 올리기

confidence가 낮거나 리스크가 크면 코드가 실행을 멈추고 사람에게 넘긴다. 자동화 시스템의 안전밸브.

Typed Output

인터페이스는 보장, 진실은 아님

출력 스키마가 맞다고 해서 내용이 맞다는 뜻은 아니다. 신뢰는 대상 도메인에서의 검증으로 얻어야 한다.

예: 환불 티켓 분류 자동화. 코드가 티켓 본문(state)을 채우고, "이 티켓은 환불/배송문의/기술지원 중 무엇인가?"(Choice)를 묻는다. 환불로 판단되면 "환불 정책 위반인가?"(Noul)를 이어서 물은 뒤, 금액과 confidence에 따라 자동 승인 / 담당자 검토(escalation)를 갈라 준다. 이 한 줄이 Rung 3(에이전트)의 축소판이기도 하다.
03 · The Ladder

AI 자동화의 다섯 개 기술 계층

LLM, RAG, Workflow, Agent, Agentic AI. 이것들은 벽이 아니라 사다리다. 각 계층은 아래 계층이 표현하지 못하는 것을 증명할 때만 올라간다.

서사는 단순하다. 시스템은 한 번에 하나의 좁은 판단을 수행하고, 필요에 따라 다음 판단으로 넘어간다.

이 판단의 단위(state·criteria)와 confidence, 그리고 코드가 소유하는 경계가 계층 전체를 결정한다. 계층이 올라갈수록 평가(evaluation)도 어려워진다 — LLM은 output 하나를 점검하면 되지만, RAG은 retrieval과 faithfulness를 함께, Agent는 trajectory(행적 전체)를, Agentic AI는 outcome과 per-agent attribution(누가 기여했는가)을 점검해야 한다.

계층 핵심 판단 상태(State) 대표 실패 대표 비용
Rung 1 · LLM 변환 / 분류 / 초안 없음 (프롬프트가 곧 저장소) 환각, 출처 없음 flat · 낮음
Rung 2 · RAG 검색 필요? 무엇을 근거로? index (소유한 사실) retrieval 실패 flat + index 유지
Rung 2.5 · Workflow 단계 분기 (트리거/분류) code 경로 불일치 예측 가능
Rung 3 · Agent 다음 행동 선택 task state silent wrong completion variable · tail
Rung 4 · Agentic AI 조율 / 평가 shared state inter-agent misalignment fan-out · coordination
Rung 1 · Large Language Model BASE · ONE CALL, NO STATE
한 줄 비유아주 유능한 작가. 뭐든 쓸 수 있고 분류·요약도 잘하지만, 모르는 것도 그럴듯하게 쓴다 — 그리고 이를 인정하지 않는다. 사실 확인은 독자(우리)의 몫이다.

시스템은 입력을 받아 "필요한 변환이 무엇인가"를 판단하고 그 변환을 수행한다. LLM은 모델 호출 한 번으로 이 작업을 수행하며, 상태를 두지 않는다. 프롬프트가 곧 저장소이고, 문맥이 곧 입력이다. 다음 호출을 위해 아무것도 기억하지 않는다.

실제 사례 고객지원팀의 티켓 분류기. 하루 2,000건의 문의가 들어오면, LLM이 한 번 호출로 각 티켓을 카테고리(환불/배송/기술지원/호환성)로 분류하고 3문장 요약을 붙여 인바운드 큐에 태그를 단다. 사람은 결재판을 스캔하듯 훑기만 하면 된다. 같은 패턴으로 리포트 초안 작성, 문장 다듬기, 명시적으로 준 데이터에 대한 추론(예: 붙여준 계약서 조항 요약)도 이 계층이다.

기술적 깊이

변환, 요약, 분류, 추출, 초안 작성, 제공된 자료에 대한 추론이 이 계층의 경계에 있다. 반면 환각, 지식 마감, 출처 없음, 행동 부재라는 실패는 모두 같은 문제를 다른 표면으로 드러낸다. 모델이 스스로 사실을 구분하지는 못한다 — 가능성 높은 다음 토큰을 만드는 것과 진실을 말하는 것은 다른 문제다.

⚠ 여기 넘어가는 순간 (계층 상승 신호)
  • 답에 내부 데이터(사내 정책, 고객 이력, 최신 가격)가 필요해질 때 → Rung 2. 출처가 없는 매끄러운 답은 여기서 위험이 된다.
  • 한 번의 호출로 끝나지 않고 여러 도구, 여러 단계가 필요해질 때 → Rung 2.5.

Jev으로의 치환

이 계층은 시스템이 묻는 첫 번째 좁은 판단에 해당한다. 질문이 그 자체로 단일 신호이고, state는 prompt이며, criteria는 출력 스키마가 된다. confidence는 분포의 수준을 요약할 뿐 전체 작업의 정확성을 주장하지 않는다 — 높은 confidence로도 환각은 가능하다.

근거 링크: LLM vs RAG vs Agent 계층 구조 · 계층별 평가 난도는 별첨 2 참고

Rung 2 · Retrieval-Augmented Generation GROUNDING · RETRIEVAL THEN ONE CALL
한 줄 비유오픈북 시험. 답을 먼저 지어내는 게 아니라 필요한 페이지를 먼저 찾아 펴 놓고, 그 페이지의 내용만으로 답하는 방식. "내가 소유한 사실"을 근거로 갖는다는 점이 Rung 1과의 본질적 차이다.

시스템이 소유한 사실이 프롬프트로 들어오지 않을 때, retrieval이 개입한다. 시스템은 "검색이 필요한가"를 먼저 판단하고, 필요하면 관련 청크를 고른다. 근거로 채운 문맥 위에서 LLM이 마지막 한 번 호출된다. 이 판단도 마찬가지로 좁은 신호(질의 우선순위·질의 재구성)에 묶인다.

실제 사례 사내 매뉴얼 챗봇. "이 제품의 보증기간은 얼마인가?"라고 물으면, 시스템이 매뉴얼을 청크로 쪼개둔 색인에서 관련 문단을 검색하고, 그 근거를 인용하며 답한다. 근거 표시 때문에 답을 믿기 쉬워지지만 — grounded는 정확함을 의미하지 않는다. 인용된 근거 자체가 옛 버전일 수 있다(⑥ stale index).

기술적 깊이

"왜 RAG이 틀리는가"를 줄일 때도, 실패 원인은 답변 문장이 아니라 근거 수급 단계에 가까운 경우가 대부분이다. 위 6계층 중 어느 관문에서 걸렸는지부터 분류해야 개선 비용이 줄어든다. 예를 들어 ⑤(retrieved-and-ignored)는 근거를 문맥에 넣었는데 모델이 무시한 경우이고, ⑥(stale index)은 색인 자체가 옛 문서를 가리키는 경우다. 관문별로 원인이 다르니 처방도 전부 다르다.

retrieval을 agent로 승격시키면(질의를 스스로 다시 쓰고, 반복 검색하고, 결과를 검증하는) 같은 질의 세트에서 성공률은 확실히 오른다. 단, 비용은 급등한다. 같은 100개 쿼리 실험에서 agentic retrieval은 RAG 대비 성공률 +14점을 얻었지만 질의당 토큰 소모는 약 36배, 응답 지연은 약 2.5배에 달했다. 늘 승격이 정답이 아니라, 질의 난이도 분포에 따라 승격 여부를 결정해야 한다.

📊 실험 수치 전체와 해석 (별첨 3 전문) 
# 같은 100개 쿼리에서 단일 검색 RAG 대비 agentic retrieval
성공률:            +14 pt    (더 많은 질의에서 정답 근거 확보)
토큰 소모:         약 36 배  (반복 검색 라운드·링크 팔로우 포함)
지연 시간:         약 2.5 배 (순차적 다중 검색·결과 확인)

"성공률을 얼마나 사려면 비용이 얼마 드는가"가 결론이다. 간단한 FAQ에는 단일 검색 RAG로 충분하고, 어려운 다단계 질의에만 agent 검색을 승격시키는 하이브리드 라우팅이 실무 정답이 되는 게 일반적이다.

⚠ 여기 넘어가는 순간 (계층 상승 신호)
  • 근거를 찾는 것 말고 찾은 뒤 여러 단계의 처리(분류→추출→검증→라우팅)가 필요해질 때 → Rung 2.5. 실행 경로를 코드로 고정하는 쪽이 저비용·고신뢰다.
Jev 치환 — 검색 필요 판단은 이렇게 구성한다
  • 질문 1: "이 요청은 답하기 위해 사내 문서가 필요한가?" → Noul. true면 검색 경로로.
  • 질문 2: "검색된 문단들 중 질의와 연관된 것은?" → Score로 관련도를 매기고 상위 조립.
  • 질문 3: "아래 답변의 각 포인트는 표기된 근거 문단으로 증빙되는가?" → faithfulness Noul로 마지막 검증.

근거 링크: Anthropic — workflow vs agent 구분 원문

Rung 2.5 · Workflow ORCHESTRATION · PREDEFINED CODE PATHS ⭐
한 줄 비유요리장이 레시피를 미리 정한 주방. 요리사(LLM)는 각 단계에서 요리를 잘하면 되지만, 무엇을 언제 해야 하는지는 레시피(코드)가 이미 정하고 있다. 실행 경로가 예측 가능하여 테스트와 통제가 쉽다.

LLM과 도구를 조율하는 방식이 가장 중요하다. Workflow는 LLM과 도구를 사전에 정의된 코드 경로로 오케스트레이션한다. 반면 Agent는 LLM이 스스로 프로세스를 동적으로 지시하는 방식(다음 Rung)이다. 코드가 유연성을 희생하는 대신 얻는 것은 예측 가능성이다. 실측된 프로덕션 분석에서 대부분의 사례가 이 계층에 속했다.

실제 사례 계약서 검토 파이프라인. 고객 계약서가 들어오면 코드가 정한 고정 루트로 흐른다: 문서 형식 판별(Choice) → 핵심 조항 추출(추출) → 표준 템플릿 대비 차이점 비교(Compare) → 검증(Noul: 추출한 조항이 원문에 실제로 근거가 존재하는가?) → 교정 초안 생성 → 평가자 점검(Score) → 담당자 전달. 각 단계는 서로 다른 좁은 판단이며, 흐름의 순서는 코드가 소유한다. "계약서가 아니다"라는 분류가 나오면 근거 문서 요청으로 분기하고, "지원하지 않는 언어"라는 판단이 나오면 언어별 담당자에게 라우팅한다.

청구서 지급 처리 같은 금융 workflow도 동일하다: 결제 이벤트 발생 → 청구서 필드 추출 → 규칙 검증 → 예외는 사람에게. 실패가 "이 경로에 진입했는데 예기치 않은 입력 형식"처럼 한 지점에 국한되므로, 실패 원인 추적(tracing)이 정확하고 쉽다.

기술적 깊이

위 5가지 패턴을 모두 읽은 조직만이 "workflow냐 agent냐"를 신뢰성 있게 논할 수 있다. 이들의 공통점은 실행 경로가 코드에 예측 가능하게 실려 있다는 것 — QA(테스트)를 각 패턴에 독립적으로 넣을 수 있고, 실패가 어떤 단계에서 발생했는지 정확하게 확정할 수 있다. Agent에 비해 유연성은 낮지만, 예측 가능성과 저비용이 우위다. 실측 프로덕션에서 대부분의 운영 사례가 그런 이유로 여기에 있었다.

⚠ 여기 넘어가는 순간 (계층 상승 신호)
  • 경로를 미리 쓸 수 없는 상황 — 다음 단계가 이번 판단 결과에 달려 매번 달라질 때 → Rung 3.
  • 예: "이번 검색 결과에 따라 조사할 문서가 달라지고, 그 결과에 따라 결론 분기가 또 달라지는" 원인 규명형 작업.
Jev 치환 — 분기점이 곧 질문이다
  • routing 패턴의 분기점 — "이 입력은 라우팅 기준 A/B/C 중 어느 것?"을 Choice 확률로. criteria가 2개면 dry-run 병렬 질의로 리스크를 덜 수 있다.
  • evaluator-optimizer 패턴 — "아래 초안이 기준 5개를 충족하는가?"를 각각 Noul로 뽑고, 기준별 통과 확률을 모아 최종 점수를 만든다.
  • orchestrator-workers 패턴 — "각 worker가 넘겨준 결과를 그대로 믿지 말라"는 원칙에 따라 오케스트레이터 자체가 검증 질문 하나를 더 얹는다.

근거 링크: Anthropic — 5가지 패턴 상세 (chaining, routing, parallelization, evaluator-optimizer, orchestrator-workers)

Rung 3 · AI Agent DYNAMIC · MODEL DIRECTS ITSELF
한 줄 비유목표만 주고 스스로 일하는 직원. 메뉴얼(레시피)이 없어도 "이건 이렇게, 저건 어떻게"를 본인이 결정하며 일을 진행. 유연하지만, 관리자(우리)가 무엇을 어떻게 했는지 눈으로 봐야 관리 가능하다.

경로가 예측 불가능해질 때 등장한다. Goal과 task state를 두고 plan → act → observe를 반복한다. 이때 시스템은 매 단계에서 "다음 행동은 무엇인가"라는 판단을 내린다. 코드는 안전장치(도구 권한, 단계 상한, 검증)를 놓아두는 정도로만 개입한다.

실제 사례 고객 환불 처리 에이전트. 환불 요청이 들어오면: 요청 글 분석(관련 정보 추출) → 주문·정책 확인(도구 호출) → 반품 근거 기록(task state) → 환불 결정 → 고객 응답 초안 작성 → 검증 후 회신. 각 절차를 어떤 순서로, 몇 번 수행할지 매번 스스로 계획하며, 요청마다 경로가 다르다. 이것이 Rung 2.5(정적 코드 경로)와 Agent(동적 자기 지시)의 경계다. 코딩 에이전트(버그 수정: 빌드 로그 읽고 → 파일 편집 → 테스트 실행 → 결과 관찰 → 수정 반복)도 같은 구조다.

기술적 깊이

오류는 누적된다. 단일 단계 성공률 p인 작업을 독립적으로 n단계 수행하면 전체 성공률은 pⁿ으로 떨어진다. 95%의 단일 단계도 10단계면 대략 60%, 20단계면 대략 36%다. 이 때문에 에이전트 설계에는 단계 실패 시 즉시 재시도하거나 사람에게 escalation하는 검증 로직이 필수다 — 검증 없이 단계만 늘리면 할수록 전체 성공률이 기하급수적으로 무너진다.

self-conditioning도 주의해야 한다. 자기 과거 실패가 맥락(대화 이력)으로 그대로 들어오면 다음 단계의 오류율이 실제로 상승한다. 처방은 "실패 로그를 살려두고 계속 참조"가 아니라, 상태 공간을 정밀하게 재설계하고 실패 정보를 "재시도 힌트" 형태만 남기고 판단 컨텍스트에서 정리하는 것이다.

그리고 이 Rung의 최대 함정은 silent wrong completion이다 — 실패한 상태인데 "완료다"라고 스스로 선언하고 성공처럼 딱딱 끝나는 경우. 검증 단계(Noul)를 state machine에 정규 절차로 넣어 독립적으로 체크해야만 누적 오류가 관찰된다. 명확한 원칙: "실패 신호가 없어도 성공 판정 없음." 성공은 반드시 검증 질문이 통과했을 때만 확정한다.

🧮 pⁿ 붕괴 — 실제 계산 예시 
# 단일 단계 성공률 95% (p = 0.95)
n = 10 단계 → 전체 성공률 ≈ 0.95^10 ≈ 60%
n = 20 단계 → 전체 성공률 ≈ 0.95^20 ≈ 36%
n = 30 단계 → 전체 성공률 ≈ 0.95^30 ≈ 21%
# 단계별 "검증 후 재시도" 규칙이 없으면
# 이 숫자가 그대로 실제 실패율로 쌓인다
🧪 self-conditioning 실험 팁

성공한 실행과 실패한 실행을 나눠서, 실패 직후 라운드의 오류율을 성공 직후 라운드와 비교해 보라. 실패 이력이 컨텍스트에 그대로 남아 있으면 이후 판단이 나빠지는 현상이 실측된다. 대안: 실패의 원인 키(어떤 변인에서 틀렸는가)만 task state에 구조화해서 남기고, 대화 이력에서는 실패 텍스트를 정리한다. "실패 기록 참조"와 "실패 텍스트 노출"은 다르다.

Jev 치환 — 에이전트 루프의 판단
  • 행동 선택 → Choice ("다음 도구/문서/문의 채널 중 어느 것?")
  • 각 단계의 검증 → Noul ("이 단계의 결과가 기준을 충족하는가?")
  • 진행 방향 확인 → Score ("이 경로로 얼마나 더 진행했는가?" 1~5 수준)
  • 임계값 미달 → Escalation (사람이 확인할 수 있도록 맥락 번들을 남겨서 넘긴다)
정책 — agent가 스스로 성공을 선언하지 못하게 한다

에이전트의 "완료" 선언은 입력으로 취급하되 출력으로 취급하지 않는다. 코드가 소유한 검증(Noul 질문)이 통과할 때만 task state가 완료로 간다. 검증 질문은 누적되어야 하는 기준 — 즉 이 작업의 사전 정의된 성공 범주 — 로 고정해 두면, 판단의 누적 신뢰성이 높아진다.

Rung 4 · Agentic AI ORCHESTRATED · ORCHESTRATOR + SHARED STATE
한 줄 비유전문가 팀 + 팀장. 리서처, 글쓴이, 검토자가 각자 일하고 팀장(오케스트레이터)이 결과를 취합·검수. 그러나 팀원들이 서로 같은 뜻을 다른 뜻으로 이해하는 실수(misalignment)가 따른다. 당연하게도 전문가 수만큼 비용·관리가 든다.

여러 에이전트가 필요할 때. 오케스트레이터가 공유 task state 위에서 독립적인 하위 작업으로 질문을 쪼개고, fan-out → 평가 → 조정 → escalation을 조율한다. 기본 원칙은 에이전트 간 출력은 디폴트로 신뢰할 수 없다다.

실제 사례 리서치 팀(오케스트레이터 + 하위 에이전트). 질문 하나가 들어오면 오케스트레이터가 이를 분해해서 여러 개의 sub-query(예: "경쟁사 A의 스택", "경쟁사 B의 시장 사례", "규제 관련 조사")로 나누고, 각 하위 에이전트가 독립적인 검색과 정리를 수행한다. 여기서 미묘한 특권이 생긴다 — 병렬 sub-query 각각은 검색·링크 팔로우·요약에 자기만의 토큰과 시간 예산을 쓰기 때문에, 단일 에이전트보다 각 주제를 깊게 파고들 수 있다. 대신 오케스트레이터는 각 결과를 무조건 합쳐서는 안 되고, 질문을 기준으로 검수한 뒤 병합한다.

기술적 깊이

멀티에이전트 실패의 대부분은 base model의 한계가 아니라 specification(명세)·design, 상호 정렬, 검증 문제다. Multi-Agent System Failure Taxonomy(MAST) 분석은 실패 원인을 세 구성 요소 42% / 37% / 21%로 분해했다. 이는 "더 좋은 모델을 도입하면 해결"이 아니라, 명세·오류 구조·에이전트 간 검증 체계를 개선해 대부분 해결된다는 의미다. 오케스트레이션 비용은 규모에 따라 부하(fan-out 배수 토큰 소모)되는 동시에, 각 에이전트의 행적을 E2E로 추적 가능하게 하는 것이 설계의 핵심이다.

📊 MAST 42 / 37 / 21 — 무엇을 의미하는가 (별첨 1 ↔ 원문) 
# Multi-Agent System Failure Taxonomy (MAST) — 실패 원인 분해
specification & system design      ≈ 42%  (명세/설계)   — 일을 잘못 쪼개고, 경계 협상이 엉킴
inter-agent (mis)alignment         ≈ 37%  (에이전트 사이) — 정보 오류를 서로 믿고 전파
verification / oversight           ≈ 21%  (검증 부족)   — 이상한 결과가 그대로 통과함

실무 시사점: 오류의 절반가량(42%)이 "모델이 틀려서"가 아니라 "우리가 명세를 잘못 쪼개서"다. 각 에이전트가 받는 기준(criteria)과 동일한 spec 공유, output 스키마 통일, 검증 질문 의무화만으로도 상당 부분의 실패가 사라진다. 이는 "더 좋은 모델" 대신 "더 좋은 명세와 검증 체계"가 수익 왕복이 빠르다는 방향을 제시한다.

⚠ 여기 넘어가는 순간 (계층 상승 신호)
  • "여러 에이전트가 진짜 필요한가?" — (1) 하나의 agent 수준에서는 커버가 안 되는 작업 분량이고, (2) 병렬화로 얻는 속도·심층성이 조정 비용보다 크고, (3) 공유 state와 명세를 관리할 준비가 되어 있을 때만 올라간다. 아니면 Rung 2.5~3 수준이 정답이다.
Jev 치환 — 오케스트레이터의 판단
  • 작업 분해 → Score로 하위 작업 중요도를 매긴 뒤, 오케스트레이터가 우선순위에 따라 배분한다.
  • 감독 → 각 하위 에이전트의 output에 독립적인 Noul 검증 질문을 하나씩 부여한다. (예: "이 결과는 질문 scope 안에 담겼나?")
  • 취합 뒤 최종 결과가 quality 필터 임계 미달이면 최상위 Escalation으로 넘긴다.
  • Confidence는 각노드에서 어째서 갈렸는지 보여줄 뿐, "전체 워크플로우의 정확도 보증"은 아니라는 점을 유지한다.

04 · Trends

2026년 AI 자동화의 흐름

여덟 가지 흐름이 동시에 진행된다. 각 흐름은 "툴이 바뀐다"가 아니라 "운영 방식이 바뀐다"로 읽어야 한다.

1

에이전트가 자동화의 주체가 되었다

자동화(script) → 자율 수행(agent). 도구가 "일하게" 되었고, 트리거·맥락·도구호출·승인의 조합이 기본 구조가 되었다.

2

멀티에이전트 오케스트레이션

아키텍처의 다음 단계. 단일 에이전트가 아닌, 공유 state 위에서 여러 에이전트가 조율되는 구조다. 조정 비용 관리가 관건이다.

3

AI가 워크플로우 안으로 삽입

one-off 생산성 도구의 한계를 넘어, 실제 프로세스 내부 단계(수동 검토·필터링·요약)를 자동으로 수행하는 방향으로 이동했다.

4

거버넌스가 플랫폼으로

가이드라인 문서가 아니라, 플랫폼 자체 기능(권한, 승인 게이트, 감사 로그, 검증)이 기본 탑재된다.

5

데이터 readiness가 전제

신뢰할 수 없는 데이터 위에 에이전트를 올리면, 스타트 시점부터 부실하다. 데이터 정제·준비가 자동화의 전제조건이 되었다.

6

인간 검토 = 설계 요구사항

HITL(Human-in-the-loop)이 "나중에 검토 버튼"이 아니라 아키텍처의 필수 구성 요소(승인 게이트·로깅)가 되었다.

7

시장이 구현 중심으로

논의 중심 — "개념으로 있을 AI"가 아닌, 실제 배포·운영·측정으로 화려한 프로젝트 리스트의 대상이 이동했다.

8

가치 측정의 이동

task savings(시간 감소)에서 운영 지표(cycle time, quality, decision impact의 질)까지 측정 대상이 이동했다.

05 · Use Cases

자동화할 일을 고르는 기준

자동화는 너무 많이 시작하면 실패한다. 높은 빈도 + 잘 측정 가능 + 데이터 뒷받침 + 낮은 위험 조건을 골라야 한다. 자동화의 실패 대부분이 "리스트가 너무 길다"에서 시작된다.

단계 방향 비중 (왜 여기에 있는가) 전제 조건
① 지금 시작 티켓 요약 · 리포트 해석 · 리드 정제 · 문서 인덱싱 · 예측 리마인더 · 지식 검색 빈도 조건을 충족하고 재사용되며, 실패해도 회수 쉬운 작업 별도 통합 미요 — 내 기존 프로세스 안에서 실행
② 확장 케이스 라우팅 · 금융 마감 지원 · 수요 예외 처리 · CRM 정비 · 계획 편차 알림 · 조달 검토 시스템 통합이 필수이고, 비즈니스 소유자가 존재하는 절차 거버넌스 강화 + 비즈니스 소유자 명시
③ 후순위 자율 협상 · high-risk decisioning · 멀티에이전트 실행 · 규제 대상 고객 결정 등 blast radius가 크고, 책임 구조·감사 조직이 아직 비어 있음 ①②에서 쌓은 근거·거버넌스·eval 없이는 금지
06 · 90-Day Plan

90일 실행 서사

하루 단위가 아니라, 관리 가능한 슬라이스부터 시작한다. 진단 → controlled slice → hardening → 확장 판단의 4단계다.

첫 15일 · 진단. 자동화할 workflow 하나를 고르고, 그 앞에서 데이터와 핸드오프를 매핑하며, 리스크와 기준 KPI를 정한다. 이 단계에서 성공 지표가 바르게 잡혀야 이후의 "성공"이 의미가 있다. "AI 도입"이 아니라 "어떤 지표가 얼마나 나아졌는가"로 논거 기준을 세워야 한다.

16일부터 45일 · controlled slice. 데이터 연결과 첫 AI capability를 구성하고, review rule을 설계하고, 출력을 테스트하고, workflow visibility를 만든다. 여기서 가장 작은 자동화가 실제 데이터 위에서 돌아가는지 검증한다. 사람 승인 단계가 아직 남아 있는 상태로 구동하는 것이 이 단계의 특징이다.

46일부터 75일 · hardening과 integration. 권한, observability, 예외 처리, 로깅, 비용 모니터링, 사용자 피드백 루프를 붙인다. 운영 ready 여부를 비즈니스, IT, 거버넌스가 같이 평가하도록 만든다. 이 단계의 산출물은 성능이 아니라 신뢰할 수 있는 시스템의 증거다.

마지막 15일 · training과 scale decision. 사용자 교육, adoption 추적, 지표 정돈, 교훈 정리, 그리고 다음 workflow 선택. 자동화는 한 번에 크게 늘리지 않는다 — 다음 workflow도 이 90일을 반복하며 늘어난다.

성과는 task savings(시간 절감)가 아니라 프로세스 결과로 측정한다.

Cycle time Quality Decision impact Adoption

"시간을 줄였다"는 절반 안내이다. 사람이 그 시간에 좋은 일을 더하는지(예: 더 많은 고객 상담, 더 높은 문서 품질, 더 신속한 대응)이 성과의 본체다.

07 · Governance

자율성에 따른 통제 설계

자율성이 올라갈수록 blast radius(실수가 미치는 범위)가 커진다. 통제 레벨은 자동화의 무게에 비례해서 올릴 것.

에이전트 설계에는 tool permission(도구별 권한), approval gate(승인 게이트), step cap(단계 한도), 검증 단계가 필요하다. confidence가 낮은 판단은 escalation으로 넘긴다. 핵심 원칙은 그 이상도 그 이하도 아니다.

  • tool permission — 도구별 읽기/쓰기/삭제 권한을 최소한으로. 삭제·결제·외부 발신 툴은 별도 게이트.
  • approval gate — 사람 승인 없이 넘어가지 말아야 하는 판단(금액·계약·규제 대상 고객 결정)에 게이트 설치.
  • step cap — 에이전트가 무한 루프로 토큰을 소모하거나 행동을 반복하는 것을 방지하는 상한선.
  • 검증 단계 + confidence 임계 — 낮은 confidence에서는 escalation. 성공 판정은 "검증이 통과했는가"라는 검증 질문으로만 내린다.
08 · Lessons

흔한 실수

자동화의 실패 대부분은 "선행 조건"에서 만들어진다.

  1. tool부터 골랐다. workflow와 성공 지표를 정하지 않은 채 프레임워크·벡터DB·에이전트 플랫폼부터 고른다. 해결: 화면 밖에서 "어떤 결과를 바꿀지" 먼저 정하기.
  2. 고장난 프로세스를 그대로 자동화했다. 이미 비효율이었던 프로세스가 → 더 빠르게 비효율이 되었을 뿐이다. 해결: 자동화 전에 프로세스 정리.
  3. 데이터를 확인 안 했다. 신뢰할 수 없는 데이터 위에 자율 행동을 수행하도록 두었다. 해결: 데이터 readiness 검토를 전제조건으로 명시.
  4. governance를 뒤로 미뤘다. 90일 로드맵의 hardening 단계를 "괜찮으니 나중에"로 미룬다. 해결: day 1부터 risk 분류·권한·감사 기록을 설계에 포함.
  5. evaluation 없이 AI output을 썼다. 데이터 분포가 바뀌어도 성능 보장을 알 수 없다. 해결: 계층별 실패 분류 체계에 맞춰 계층별 evaluation을 놓는다.
  6. 시간 절감만 봤다. task savings만 봐서 business 영향을 알 수 없다. 해결: cycle time·quality·decision impact·adoption으로 측정 확장.
  7. 에이전트를 지원 체계 없이 확장했다. ownership(소유자)·monitoring·cost governance 없이 대량 scale했다. 자동화는 도구의 문제가 아니라 운영의 문제다.

별첨 2 · 계층별 evaluation 종합 EVAL 
# "뭘 얼마나 잘 보는가"가 계층별로 다르다 (각 계층 = 자체 평가 must)
Rung 1 LLM     : output(단일 답) 체크                    ← 변환 정확도 · 분류 일관성
Rung 2 RAG     : retrieval + faithfulness 체크           ← 근거 유무까지 포함
Rung 2.5 WF    : 단계별 데이터 흐름 체크                 ← 경로 · 라우팅 정확성
Rung 3 Agent   : trajectory(행적 전체) 체크              ← 저비용 실선 · 지연 상환
Rung 4 Agentic : outcome + per-agent attribution 체크    ← 누가 무엇을 기여했는가 추적

계층이 올라가면 평가 대상이 "점수 하나"에서 "과정 전체"로 이동한다. 이 때문에 Rung 3 이상에서는 tracing(각 단계에서 무엇이 관찰되었는가, 어떤 판단이 내려졌는가)을 확보해야 한다. 이 기반이 있어야 문제를 "감이 나쁨" 상태가 아니라 "다음 개선 입력"으로 바꿀 수 있다.
