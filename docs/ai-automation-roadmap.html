왜 지금 AI 자동화가 다른가

과거의 AI 자동화는 챗봇에게 질문에 답하게 하는 것이었다면, 지금의 AI 자동화는 AI가 업무를 수행하는 방향으로 진화하고 있다. 반복 업무는 AI가, 전략 수립과 감독, 최종 결정은 인간이 담당한다.

AI 자동화의 시대적 이동은 한 문장에 압축된다. 자동화 대상이 개별 작업(task)에서 업무 프로세스(workflow)로 이동했기 때문이다.

2026년에는 에이전트가 트리거를 감지하고, 맥락을 해석하고, 도구를 호출하고, 사람에게 승인을 요청하는 구조가 등장했다. Gartner는 task-specific AI agents가 엔터프라이즈 애플리케이션의 상당 비율로 확산되는 것을 전망했고, McKinsey는 2025년에도 agentic AI를 scaling하는 조직과 experimenting하는 조직이 동시에 존재했다. 실제 운영 사례 분석에 따르면 프로덕션 시스템 대부분이 여전히 사전에 정의된 구조화된 워크플로우에 속한다.

따라서 이 로드맵은 기술의 깊이를 먼저 쌓고, 그 위에 실행 전략을 얹는다. 기술이 깊을수록 자동화가 신뢰받고, 실행이 명확할수록 성과가 남는다.

핵심 원칙 — 워크플로우를 먼저 고르고, 도구는 그다음이다.

AI 자동화의 다섯 개 기술 계층

LLM, RAG, Workflow, Agent, Agentic AI. 이것들은 벽이 아니라 사다리이며, 각 계층은 아래 계층이 표현하지 못하는 본질적 이해라는 점을 반복해서 증명한다.

서사는 단순하다. 시스템은 한 번에 하나의 좁은 판단을 수행하고, 필요에 따라 다음 판단으로 넘어간다. 이 판단의 단위와 그에 대한 confidence, 그리고 코드가 소유하는 경계가 계층 전체를 결정한다.

평가의 난이도는 계층이 올라갈수록 배가된다. LLM은 output 하나를 점검하면 되지만, RAG은 retrieval과 faithfulness를 함께, Agent는 trajectory를, Agentic AI는 outcome과 per-agent attribution를 점검해야 한다. 그래서 각 계층은 자신의 판단 단위에 맞는 평가를 별도로 갖춰야 하고, 평가 자체가 곧 다음 개선의 입력이 된다.

계층 핵심 판단 상태 대표 실패 대표 비용
Rung 1 · LLM 변환 / 분류 / 초안 없음 환각, 출처 없음 flat · 낮음
Rung 2 · RAG 검색 필요? index retrieval 실패 flat + index
Rung 2.5 · Workflow 단계 분기 code 경로 불일치 예측 가능
Rung 3 · Agent 행동 선택 task state silent wrong completion variable · tail
Rung 4 · Agentic AI 조율 / 평가 shared state inter-agent misalignment fan-out · coordination
Rung 1 · Large Language Model BASE · ONE CALL, NO STATE

서사의 첫 단계에서 시스템은 입력을 받아 필요한 변환이 있는지만 판단하고, 그 변환을 수행한다. LLM은 모델 호출 한 번으로 이 작업을 수행하며, 상태를 두지 않는다. 프롬프트가 곧 저장소이고, 문맥이 곧 입력이다.

기술적 깊이

변환, 요약, 분류, 추출, 초안 작성, 제공된 자료에 대한 추론이 이 계층의 경계에 있다. 반면 환각, 지식 마감, 출처 없음, 행동 부재라는 실패는 모두 같은 문제를 다른 표면으로 드러낸다. 모델이 스스로 사실을 구분하지는 못한다.

Jev으로의 치환

이 계층은 시스템이 묻는 첫 번째 좁은 판단에 해당한다. 질문이 그 자체로 단일 신호이고, state는 prompt이며, criteria는 출력 스키마가 된다. confidence는 분포의 수준을 요약할 뿐 전체 작업의 정확성을 주장하지 않는다.

Rung 2 · Retrieval-Augmented Generation GROUNDING · RETRIEVAL THEN ONE CALL

시스템이 소유한 사실이 프롬프트로 들어오지 않을 때, retrieval가 개입한다. 시스템은 검색이 필요한가를 판단하고, 필요하면 관련 청크를 고른다. 이 판단도 마찬가지로 좁은 신호에 묶인다.

기술적 깊이

실패 분류는 generation 실패가 아니라 retrieval 실패에 가깝다. corpus gap, chunking, semantic gap, ranking, retrieved-and-ignored, stale index라는 여섯 계층을 통과해야 한다. grounded는 정확함을 의미하지 않는다.

비용의 본질

retrieval을 agent로 승격시키면 같은 질의에 대해 성공률은 오르지만 비용은 배가 된다. 같은 100개 쿼리 실험에서 agentic retrieval은 RAG 대비 성공률에서 +14점을 얻었지만 비용은 36배, latency는 2.5배가 추가로 소요됐다.

Rung 2.5 · Workflow ORCHESTRATION · PREDEFINED CODE PATHS

LLM과 도구를 조율하는 방식이 가장 중요하다. Workflow는 LLM과 도구를 사전에 정의된 코드 경로로 오케스트레이션하는 반면, Agent는 LLM이 스스로 프로세스를 동적으로 지시하는 방식이다. 코드를 작성하는 것이 경량이고, 능동성이 무게다.

기술적 깊이

prompt chaining, routing, parallelization, evaluator-optimizer, orchestrator-workers. 실행 경로가 예측 가능하면 workflow이 곧 최선이다. 실측된 프로덕션 분석에서 대부분의 사례가 workflow에 속했다.

Rung 3 · AI Agent DYNAMIC · MODEL DIRECTS ITSELF

경로가 예측 불가능해질 때 등장한다. Goal과 task state를 두고, plan, act, observe를 반복한다. 이때 시스템은 매 단계에서 다음 행동을 선택하는 판단을 내린다.

기술적 깊이

오류가 누적되면 p의 거듭제곱으로 전체 성공률이 붕괴된다. 자기 실수가 맥락에 들어오면 오류율이 실제로 상승하는 self-conditioning이 존재한다. 그리고 가장 위험한 silent wrong completion은 실패 신호 없이 성공으로 선언될 수 있다. 검증 단계가 state machine에 있어야 한다.

Jev으로의 치환

행동 선택은 Choice로, 검증은 Noul으로, 임계값은 confidence 기준으로 표현할 수 있다. Action을 선택하기 전에 필요한 state를 채우고, confidence가 낮으면 escalation으로 넘긴다.

Rung 4 · Agentic AI ORCHESTRATED · ORCHESTRATOR + SHARED STATE

여러 에이전트가 필요할 때. 오케스트레이터가 공유 task state 위에서 독립적인 질문들을 던지고, fan-out과 평가, 조정, 에스컬레이션을 조율한다. 에이전트 간 출력은 신뢰할 수 없다.

기술적 깊이

멀티에이전트 실패의 대부분은 base model의 한계가 아니라 specification과 design, 상호 정렬, 검증 문제다. MAST 분석에서 이를 42%, 37%, 21%로 분해했다. 오케스트레이션 비용과 동시 추적 가능성이 설계의 핵심이다.

중단 판단 체크리스트 — 순서대로 YES가 나오면 그 계층에서 멈춘다.

2026년 AI 자동화의 흐름

에이전트의 등장은 자동화의 전제를 바꿨다. 자동화가 아니라 자동 수행가 되었고, 이는 데이터, 거버넌스, 운영 모델과 깊이 연결된다. 도구 중심의 자동화는 사라지고, 프로세스 중심의 자동화가 커지고 있다.

여덟 가지 흐름이 동시에 진행된다. 첫째, 에이전트가 자동화의 주체가 되었다. 둘째, 멀티에이전트 오케스트레이션이 아키텍처의 다음 단계가 되었다. 셋째, AI가 워크플로우 안에 삽입되어 one-off 생산성 도구의 한계를 넘어설 준비가 되었다. 넷째, governance가 플랫폼으로 들어왔다. 다섯째, 데이터 기반의 readiness가 자동화의 전제가 됐다. 여섯째, 인간 검토는 설계 요구사항이 됐다. 일곱째, 시장이 구현 중심으로 이동했고, 여덟째 자동화의 가치 측정이 task savings에서 운영 모델 변화로 이동했다.

자동화할 일을 고르는 기준

자동화는 너무 많이 시작하면 실패한다. 시작할 수 있는 use case는 빈도가 높고, 측정이 가능하고, 데이터가 뒷받침되고, 위험도가 낮거나 중간이다. 티켓 요약, 리포트 해석, 리드 정제, 문서 인테로, 예측 리마인더, 지식 검색이 이 영역에 속한다.

확장 단계에서는 케이스 라우팅, 금융 마감 지원, 수요 예외 처리, CRM 정비, 계획 편차 알림, 조달 검토가 있다. 이 단계는 시스템 통합과 더 강한 거버넌스, 비즈니스 소유권이 필요하다. 후순위는 자율 협상, high-risk decisioning, 멀티에이전트 실행, 규제 대상 고객 결정, 셀프 히밍 같은 고도화다.

90일 실행 서사

하루 단위가 아니라, 관리 가능한 슬라이스부터 시작한다. 진단에서 controlled slice, hardening, 그리고 확장 판단까지의 한 편의 서사.

첫 15일은 진단이다. 자동화할 workflow 하나를 고르고, 그 앞에서 데이터와 핸드오프를 매핑하며, 리스크와 기준 KPI를 정한다. 이 단계에서 성공 지표가 바르게 잡혀야 한다.

16일부터 45일까지는 controlled slice을 만든다. 데이터 연결과 첫 AI capability를 구성하고, review rule을 설계하고, 출력을 테스트하고, workflow visibility를 만든다. 여기서 가장 작은 자동화가 실제 데이터 위에서 도는지 검증한다.

46일부터 75일까지는 hardening과 integration이다. 권한, observability, 예외 처리, 로깅, 비용 모니터링, 사용자 피드백 루프를 붙인다. 운영 ready가 되었는지 비즈니스, IT, 거버넌스가 함께 평가할 수 있게 만든다.

마지막 15일은 training과 scale decision이다. 사용자 교육, adoption 추적, 지표 운동, 교훈 정리, 그리고 다음 workflow 선택이다. 자동화는 한 번에 크게 늘리지 않는다.

성과는 task savings가 아니라 프로세스 결과로 측정한다.

자율성에 따른 통제 설계

자율성이 올라갈수록 blast radius가 커진다. low risk는 자동화할 수 있고, medium risk는 권고와 검토를, high risk는 승인과 감사를 요구한다. 금융, 헬스케어, 보상, 조달, 법무, 고객 커뮤니케이션처럼 accountability가 중요한 영역에 이 모델은 특히 강하게 적용된다.

에이전트 설계에는 tool permission, approval gate, step cap, 검증 단계가 필요하다. confidence가 낮은 판단은 escalation로 넘긴다. 그리고 agent가 스스로 성공을 판단하게 두면 안 된다는 규칙은 모든 계층에 공통으로 적용된다.

흔한 실수

자동화는 대부분의 실패를 선행 조건에서 만든다. workflow과 성공 지표를 정하지 않은 채 tool부터 선택했고, 고장난 프로세스를 자동화했으며, 신뢰할 수 없는 데이터에 action을 수행했고, governance를 뒤로 미루고, evaluation 없이 AI output을 쓰고, 시간 절감만 보고 비즈니스 결과를 보지 않았다.

마지막으로, agent scaling을 support ownership, monitoring, cost governance 없이 확장한 사례가 있다. 자동화는 도구의 문제가 아니라 운영의 문제다.
